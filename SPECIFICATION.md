# hutch — specification

**Version:** `hutch: 1` · **Status:** DRAFT. Nothing here is stable until two independent consumers
have run against it.

---

## 0. The problem, stated precisely

A CI lane depends on capabilities its host supplies: packages, shared libraries, running services,
privileges, toolchains. On a hosted runner those arrive **by accident of the vendor's image**. On a
self-hosted runner they arrive **by design, or not at all**.

Nothing enumerates the difference. So the difference is discovered by failure, one item at a time,
and each failure looks like a different problem.

`hutch` makes the difference **declarable, measurable, and checkable before the lane runs.**

---

## 1. Two documents, one verb

### 1.1 `hutch.provides.yaml` — what a host supplies

Published by whoever operates the host or builds the runner image. **Generated by measurement on
that host. Never hand-written** (see R1).

```yaml
hutch: 1
kind: provides

identity:
  id: sasha-ubuntu                 # stable name for the host or image
  image_digest: sha256:abc123...   # if containerised; omit for a bare host
  host_arch: x86_64

measurement:
  at: 2026-08-09T00:14:52Z         # REQUIRED — a capability claim expires
  by: https://github.com/o/r/actions/runs/31270809170   # REQUIRED — provenance
  tool: hutch/0.1.0

capabilities:
  - id: pkg.postgresql-client
    present: true
    version: "12.22"
    how: "psql --version"

  - id: svc.postgres
    present: true
    endpoint: host.containers.internal:5432
    how: "pg_isready accepted the connection"

  - id: runtime.docker-socket
    present: false
    deliberate: true
    reason: "the runner user's unprivilege is the security boundary"
    how: "no /var/run/docker.sock and no $DOCKER_HOST"

  - id: lib.chromium-shared
    present: false
    how: "browserType.launch → Host system is missing dependencies to run browsers"
```

### 1.2 `hutch.requires.yaml` — what a lane needs

Declared by the consuming repository, one document per lane (a lane is a CI job, not a repo).

```yaml
hutch: 1
kind: requires

lane: go-page-gate
repo: qrrabbit/baking_scheduler

needs:
  - id: pkg.postgresql-client
    min_version: "16"
    why: "every migration is applied through psql; a v12 client against a v16 server is skew"

  - id: lib.chromium-shared
    why: "the geometry probe and the Lighthouse gate each launch a browser"

  - id: svc.postgres
    why: "every measured page is served from a database built by the tracked migrations"

forbids:
  - id: runtime.docker-socket
    why: "not needed; declared so a host that has one is not silently relied upon"
```

### 1.3 `hutch check` — reconcile

Reads one `provides` and one or more `requires`, and emits a table plus an exit code.

| outcome | meaning | exit |
|---|---|---|
| `PASS` | required, present, and any version constraint satisfied | 0 |
| `FAIL` | required and absent, or present at an unsatisfying version | non-zero |
| `SKIP` | **could not be determined** | non-zero (see R3) |

A run with any `FAIL` or any `SKIP` is a failing run.

## 2. The rules that make this worth having

These are not style preferences. Each corresponds to a failure that has already happened.

### R1 — Measured, never asserted

A `provides` document is **generated by running a probe on the host it describes.** Hand-writing one
reproduces exactly the problem `hutch` exists to solve: a confident claim, unverified, that outlives
its truth.

> Evidence: of the six capability claims in [`WHY.md`](WHY.md), every one was hand-asserted by a
> competent party and measured false by another. None was carelessness.

### R2 — Provenance and expiry are mandatory

`measurement.at` and `measurement.by` are **required fields**. A consumer may reject a `provides`
document older than a threshold it sets.

> A capability claim about an environment is a measurement with an expiry — not an axiom. Record who
> measured it, when, and on what, or it hardens into folklore and gets built upon in both directions:
> requiring something nobody can supply, *and* refusing something now freely available.

### R3 — UNKNOWN blocks; it never defaults to PASS

If a capability cannot be determined, `hutch check` reports `SKIP` and **fails**. It never treats
"could not measure" as "present".

> The tempting default is to pass on unknowns so the pipeline is not blocked. That converts a gap
> into a silent gap, and a silent gap is the most expensive kind: not red, not flapping, not pending
> — a clean green history and a healthy-looking dashboard.

Some facts cannot be measured from inside at all — a process cannot always determine what owns the
resource it is talking to. Those must be **declared explicitly** by the operator, and an undeclared
value is a `SKIP`, not an assumption.

### R4 — A `provides` document is bound to an identity

It describes exactly one host or one image digest. Reusing it for "the fleet" is a category error:
replicas drift, images get rebuilt, and a document that names no identity can never be shown stale.

### R5 — A failure names the ask and its owner

`FAIL` output states what is missing, **which lane needs it, why, and who can supply it.** A checker
that reports `lib.chromium-shared: absent` has described a symptom. One that reports

> `lib.chromium-shared` absent — required by `go-page-gate` (Lighthouse and the geometry probe each
> launch a browser). Owner: the runner image. Ask: bake `libnss3 libnspr4 libasound2` + deps.

has produced the next action. The second costs one line more and saves a round trip.

### R6 — The checker carries a positive control

`hutch check` must assert something it **knows** must hold, so that a checker which has lost the
ability to measure fails its own control rather than reporting everything green.

> Failure modes sort by loudness: **crash > red > blind-and-red > green-while-blind.** Only the last
> requires a human to *suspect* something before anything is discovered, and it is the only one that
> gets worse the more you trust your dashboard. A positive control is the mechanism that converts
> green-while-blind into red-and-blind.
>
> Ask of any gate: *if this lost its ability to see, what would go red?* If the answer is "nothing",
> build the control before anything else.

## 3. Capability identifiers

Namespaced, lowercase, dot-separated. The namespace states what kind of thing it is.

| namespace | meaning | example |
|---|---|---|
| `pkg.` | an installed package or CLI | `pkg.postgresql-client` |
| `lib.` | shared libraries needed to load or launch something | `lib.chromium-shared` |
| `svc.` | a reachable running service | `svc.postgres` |
| `runtime.` | a property of the execution sandbox | `runtime.docker-socket` |
| `priv.` | a privilege the step can exercise | `priv.passwordless-sudo` |
| `tool.` | a language toolchain | `tool.go` |

**A capability id names a question, not an implementation.** `lib.chromium-shared` asks *can a
headless browser start here* — not *is package X installed*. Ids are answered by the probe however
the host makes that answerable.

### 3.1 Privileges are capabilities too — and discovering one is not the same as being granted it

`priv.` entries are declarable and measurable like any other. But a privilege that a probe finds
present, and that the host operator did not intend to grant, is **not a capability to build on** —
it is a defect in the host's configuration.

> A capability you discover but were not granted is not a capability; it is a defect in someone
> else's system, and depending on it converts their fix into your outage.

A `requires` document may therefore declare a privilege as needed *only* when the host's `provides`
marks it `deliberate: true`.

---

## 4. What this specification deliberately does not cover

- **Allocation** — which repos get runners on which hosts, and how many. That is capacity, it is the
  fleet operator's decision, and it belongs in whatever the fleet already uses to declare it.
- **Installation or remediation.** See the non-goals in the README.
- **Secrets and credentials.** A `provides` document states that a service is reachable and may name
  an endpoint. It never carries credentials.

## 5. Open questions

Recorded here rather than settled, so contributors can see what is genuinely undecided. Each becomes
a decision record in [`docs/decisions/`](docs/decisions/) when resolved.

1. **Version comparison semantics.** `min_version: "16"` against a measured `"12.22"` is
   unambiguous; arbitrary vendor version strings are not. Restrict to semver-ish, or allow a
   declared comparator per capability?
2. **Staleness policy.** Should `hutch check` reject a `provides` older than N, and is N the
   consumer's choice or the publisher's?
3. **Multiple hosts.** A repo whose lanes run on several hosts needs the checker to select the right
   `provides`. By label? By explicit reference in `requires`?
4. **Probe distribution.** The probe must run on the host, but the capability ids it answers are
   shared. How is a probe extended for a host-specific capability without forking it — which is the
   duplication this whole effort exists to prevent?
