# hutch

**Declare what your self-hosted CI runner provides. Declare what your job needs. Fail before the job does.**

When a CI job moves from a hosted runner to your own machine, it moves between *dependency sets* —
and nothing enumerates the difference. Packages that were present by accident of GitHub's image are
absent by design from yours. They surface one at a time, days apart, each as a different and
misleading failure: a build error, a "Network is unreachable", a gate that reports blind while being
perfectly correct.

`hutch` closes that gap with two documents and one verb.

| | |
|---|---|
| `hutch.provides.yaml` | what a host or runner image actually supplies — **measured, never hand-written** |
| `hutch.requires.yaml` | what a repo's lane needs from its host, and why |
| `hutch check` | reconciles the two and fails loudly, naming the ask and its owner |

## Why this is not just a README listing packages

GitHub publishes a software manifest for *their* runner images. Nobody publishes one for *yours*,
and nothing reconciles a repo's requirements against it. The result is that capability facts get
discovered by conversation — someone asserts, someone else contradicts, and days pass.

The rule that makes this different from documentation: **a `provides` document is generated by
measurement on the host it describes, and carries the timestamp and the run that produced it.** A
capability claim is a measurement with an expiry, not an axiom. Hand-written manifests become the
very assertions this replaces.

See [`WHY.md`](WHY.md) for the six capability claims that motivated this, each asserted confidently
by one party and measured false by another.

## Status

**Pre-1.0. Specification first, implementation second — deliberately.**

This is being extracted from a live migration: two independent projects moving CI onto a shared
self-hosted runner fleet, across four repositories. The specification is being written against real
failures rather than imagined ones, and the reference implementation follows once the contract holds
for both consumers.

That ordering is the point. A universal tool designed before it has a real consumer is a guess; one
extracted from two independent consumers has already survived the only test that matters.

- [`SPECIFICATION.md`](SPECIFICATION.md) — the contract (draft, `hutch: 1`)
- [`WHY.md`](WHY.md) — the evidence
- [`CONTRIBUTING.md`](CONTRIBUTING.md) — how to contribute, and where decisions are recorded
- [`docs/decisions/`](docs/decisions/) — the decision log

## Non-goals

- **It is not a build system.** It verifies the environment a build is about to run in, and does
  nothing else.
- **It does not install anything.** Discovering that a dependency is missing and quietly installing
  it is how environment drift becomes invisible. `hutch` reports; a human or an image build fixes.
- **It does not manage runners.** Allocation — which host, which roles, how many replicas — belongs
  to whoever operates the fleet. `hutch` describes capability, not capacity.
