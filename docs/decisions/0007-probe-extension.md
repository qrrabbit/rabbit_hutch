# 0007 — Probe extension: a probe is a directory of single-capability answerers, not a script to fork

- **Status:** proposed
- **Date:** 2026-08-09
- **Resolves:** SPECIFICATION.md §5 question 4
- **Proposed by:** the voicegent architect

## Context

The probe must run on the host, but the capability ids it answers are shared. How is it extended for a
host-specific capability without forking — *"which is the duplication this whole effort exists to
prevent"*?

## Decision

**A probe is not a script. It is a DIRECTORY of single-capability answerers, discovered at run time
from two roots, and neither root is edited to accommodate the other.**

```
probes.d/                    # SHARED, lives here in rabbit_hutch, consumed by every project
  pkg.postgresql-client
  lib.chromium-shared
  svc.postgres
  runtime.docker-socket
  priv.passwordless-sudo

$HUTCH_LOCAL_PROBES/         # HOST-LOCAL, on the host, never in this repo
  svc.rocm-gpu
  pkg.whisper-cpp
```

Each file answers exactly one capability id: exits 0 for present, 1 for absent, 2 for
**could-not-determine**, and prints the `version` / `how` / `endpoint` fields the spec defines. The
runner unions the two roots; a local id shadowing a shared one is an **error**, not an override,
because a silent shadow is a fork with extra steps.

## Why this one

**Forking happens when a shared artifact must be EDITED to serve one consumer.** Making the unit of
extension a whole new file, discovered rather than registered, means the host-specific case never
touches the shared file — there is nothing to diverge. This is the same move as declaring capabilities
one-per-entry instead of as a monolithic host profile.

**One file per id also makes exit code 2 meaningful per capability.** A monolithic probe that dies
partway through emits a truncated document, and a truncated document is indistinguishable from a host
that genuinely lacks the missing entries — which is R3's failure mode arriving through the back door.
Per-id isolation contains a broken answerer to its own id.

## The rule that keeps R3 whole, and it is the important half

**The expected capability set is derived from what `requires` documents ASK FOR — never from the
probe directory's listing.**

If the checker enumerates capabilities from the probe set, then a capability **no probe answers** is
simply absent from `provides`, and the checker has to interpret a missing key. Interpreting it as
"not present" yields `FAIL` — which is safe but names the wrong owner and the wrong action, in direct
violation of R5. Interpreting it as "present" is the catastrophe R3 forbids.

The correct reading is the third one:

> **A capability that appears in a `requires` and in no `provides` entry is `SKIP` — not `FAIL`.**
> `FAIL` says *the host lacks it; ask the host's owner to supply it.* `SKIP` says *nobody measured it;
> extend the probe.* Different owner, different next action — which is exactly what R5 exists to
> produce.

This is not merely an implementation note; it is a gap in the current specification and is filed as
[0008](0008-unprobed-is-skip-not-fail.md).

## Distribution mechanics

The shared `probes.d/` lives in this repo and consumers vendor or submodule it. It is small, it has no
build, and it must be readable at the commit that produced a `provides` document — so
`measurement.tool` should carry the probe-set commit alongside the version:

```yaml
measurement:
  tool: hutch/0.1.0
  probes: rabbit_hutch@4c69e4c
```

Without it a `provides` cannot be reproduced, and R1's *"generated by measurement"* becomes
unverifiable one release later.

## On rehoming `fleet-image-probe.sh`

**Yes — move it here, and the reasoning is the operator's own no-fork ruling rather than tidiness.**
It currently lives in the `baking_scheduler` tree, where voicegent cannot consume it; a second copy
would be invisible to both repos' duplication scanners, because each scans a single tree. That is the
precise class this repo exists to prevent, so hosting the tool that prevents it in a place only one
consumer can reach would be self-refuting.

**One condition, which is this record's own decision applied to the incoming artifact:** it should
arrive **decomposed into `probes.d/` entries**, not as a monolithic script with a new home. Rehoming
it intact would move the fork risk rather than remove it — the second project's first host-specific
capability would still have to edit the shared file.
